# LibrePCB integration design

Status: design note for milestone 6 (`doc/work/006-librepcb-integration.md`). Steps 1 to 5 of section 5 are implemented on the fork's `pns-router` branch; sections 1, 3 and 4 were corrected as they were built and say so where they were. Every LibrePCB fact below is cited as `path:line` relative to the checkout at `~/dev/librepcb` (branch `master`, commit 690a4e7a7 at the time of writing). Every KiCad fact is cited through the reference notes in `doc/reference/kicad/`, which carry the KiCad line numbers.

The reader is assumed to know one of the two code bases well and the other only in outline. Section 0 is the summary; sections 1 to 4 are the design; section 5 is the work breakdown; section 6 lists what has to be asked upstream before any C++ is written.

## 0. Summary of the recommendation

The snapshot crosses the FFI as plain `#[repr(C)]` structs plus pointer and length arrays, in the style rust-core already uses for `interactive-html-bom` (`libs/librepcb/rust-core/src/ffi/ibom_ffi.rs:152` for the struct, `libs/librepcb/core/export/interactivehtmlbom.cpp:303` for the C++ side that fills it). Not a serialised byte buffer. Reasons in section 1.2.

The engine side of the FFI lives in `libs/librepcb/rust-core`, which gains a `pnsrouter` dependency next to `interactive-html-bom` (`libs/librepcb/rust-core/Cargo.toml:17`) and a `router_ffi.rs` module next to `ibom_ffi.rs`. The C++ side is a wrapper class in `libs/librepcb/editor` plus one new board editor tool state. Nothing in `libs/librepcb/core` changes.

The three riskiest parts, in order: the commit applier that turns free floating segments into `BI_NetSegment` topology (this is exactly where Urban Bruhin's 2018 attempt stopped, see section 4.6), the preview rendering path (LibrePCB's board editor has no precedent for a tool that draws without editing the document), and the layer index mapping (`Layer::getCopperNumber()` is not dense, see section 1.3).

## 1. The FFI boundary

### 1.1 What rust-core's conventions actually are

`libs/librepcb/rust-core` is a Rust crate compiled into a static library by corrosion (`libs/librepcb/rust-core/CMakeLists.txt:14`) with a C++ header generated by cbindgen at build time (`libs/librepcb/rust-core/build.rs`, configured by `libs/librepcb/rust-core/cbindgen.toml:5` for `language = "C++"` and `:7` for the `librepcb::rs` namespace). The crate is built with `crate-type = ["lib", "staticlib"]` (`libs/librepcb/rust-core/Cargo.toml:7`) and the FFI module is behind a Cargo feature so the crate stays usable without C++ (`libs/librepcb/rust-core/src/lib.rs`, the `#[cfg(feature = "ffi")] mod ffi;` block).

Four patterns are established and the router FFI should follow all four.

An owned Rust object crosses as an opaque pointer created by a `ffi_*_new` returning `*mut T` and destroyed by a `ffi_*_delete` (`libs/librepcb/rust-core/src/ffi/ibom_ffi.rs:188` and `:211`). On the C++ side it is held by `RustHandle<T>`, a move only scoped pointer that calls the deleter (`libs/librepcb/core/utils/rusthandle.h:41`, used at `libs/librepcb/core/export/interactivehtmlbom.cpp:104`).

Qt types cross by reference, never by value. `QByteArray`, `QString` and `QStringList` are opaque incomplete types on the Rust side (`libs/librepcb/rust-core/src/ffi/cpp_ffi.rs:9`, `:139`, `:168`) with hand written C++ accessors (`libs/librepcb/rust-core/ffi.cpp:35` onwards). Rust reads a `QString` through `from_qstring` (`libs/librepcb/rust-core/src/ffi/cpp_ffi.rs:150`) and writes one through `qstring_set` (`:162`).

Bulk data crosses as a C++ `std::vector` of `#[repr(C)]` structs, passed as a raw pointer plus a length. `ffi_ibom_add_footprint` takes `pads_array: *const InteractiveHtmlBomPad, pads_size: usize` (`libs/librepcb/rust-core/src/ffi/ibom_ffi.rs:305`) and the caller builds the vector inline (`libs/librepcb/core/export/interactivehtmlbom.cpp:303`). Note the comment at `libs/librepcb/core/export/interactivehtmlbom.cpp:259`: the vector is always reserved to at least one element because an empty vector's `data()` pointer made a Rust debug build panic. That is a real trap to reproduce in every array we pass.

Scalars cross as their primitive type and `Length` crosses as a bare `i64` (`libs/librepcb/rust-core/src/ffi/length_ffi.rs`, whose module doc says exactly that).

### 1.2 Recommendation: structs, not a serialised buffer

The crate's own snapshot type landed while this note was being written and is the thing the FFI has to mirror field for field. `WorldSnapshot` (`src/snapshot.rs`) is `copper_layer_count: u8`, `max_clearance: i32`, `items: Vec<WorldItem>` and `edge_exclusions: Vec<Shape>`. A `WorldItem` is `id: HostId`, `net: Option<NetId>`, `layers: LayerRange`, `geometry: WorldGeometry`, `hole: Option<Shape>`, `flags: WorldItemFlags` (locked, routable, free pad, compound primitive) and `flashed_layers: Option<LayerMask>`, where `None` means the mask equals the layer span. `WorldGeometry` has exactly four variants, `Segment`, `Via`, `Solid` and `Hole`. `World::from_snapshot` returns the world plus a `HostIndex` that maps host ids to engine handles in both directions, one to many in the host to engine direction.

Pass that as `#[repr(C)]` structs. Concretely, one `ffi_router_snapshot_new(copper_layer_count, max_clearance)` returning an opaque `*mut WorldSnapshot`, then one push function per geometry variant (`ffi_router_snapshot_add_segment`, `_add_via`, `_add_solid`, `_add_hole`), each taking a common item header struct plus the variant's own fields, then `ffi_router_new(snapshot, rules, settings)` which consumes the snapshot and returns the opaque session. Array taking forms of the push functions are worth adding for segments and solids, which are the numerous cases on a real board.

`edge_exclusions` stays empty for LibrePCB. Its only producer in KiCad is the castellated pad case, and LibrePCB has no equivalent concept today.

The alternative, serialising the whole snapshot into a `QByteArray` and parsing it on the Rust side, is what the existing `QByteArrayWriter` (`libs/librepcb/rust-core/src/ffi/cpp_ffi.rs:65`) would make easy. Reject it for four reasons.

It has no precedent in rust-core: the byte array path exists only for zip archives, which are genuinely byte streams. Introducing a second, ad hoc wire format for structured data would be the first of its kind in the tree, and an upstream reviewer would rightly ask why.

It duplicates the schema. A serialised format needs a writer in C++, a reader in Rust, a version number, and a test that the two agree. The struct approach has cbindgen generate the C++ view of the Rust struct, so a field added on one side breaks the compile on the other. That is the property we want most, because the snapshot has roughly a dozen record types and will grow.

It hides the variable length parts anyway. Pad outlines are variable length vertex lists, so either format needs a pointer plus a length or an offset plus a length. The struct approach can carry `*const FfiVertex` plus `usize` and let the C++ side own the buffer for the duration of the call, which is exactly what `ffi_ibom_add_footprint` does with `svgs` (`libs/librepcb/core/export/interactivehtmlbom.cpp:252`).

It costs a copy of the whole board on every sync. The router re-syncs on every tool entry, and on a large board the snapshot is the dominant allocation. Pushing structs lets the Rust side build its arena directly.

The one place where a buffer wins is the regression harness: `DESIGN.md` section 8 wants a serialisable snapshot for replay. That serialisation belongs inside the pnsrouter crate as an ordinary Rust feature over `WorldSnapshot`, not on the FFI boundary. The host builds a `WorldSnapshot` through the FFI and the crate serialises it for a fixture when asked.

Geometry crosses in a small vocabulary that mirrors `Shape` (`DESIGN.md` section 3): a tagged struct with a discriminant and a union like payload flattened into fields, or, simpler and preferred, one push function per shape kind. Circles carry centre and radius, rectangles carry centre, half width, half height and corner radius, segments carry two endpoints and a width, and polygons carry a vertex array. Keeping circles and rectangles native rather than polygonising everything is the single biggest performance decision on this boundary; note 05 section 5.4 records that Horizon's fast path for those two shapes is what makes their shove interactive.

### 1.3 Layer index mapping

The engine works in dense copper layer indices `0 ..= copper_layer_count - 1`, closed intervals (`src/item.rs`, `LayerRange`). LibrePCB's `Layer::getCopperNumber()` is **not** dense: it returns 0 for top, `i` for inner layer `i`, and `innerCopperCount() + 1` for bottom (`libs/librepcb/core/types/layer.h:196` for the accessor, `libs/librepcb/core/types/layer.cpp:357` for the bottom layer's flags, `libs/librepcb/core/types/layer.cpp:384` for `innerCopperCount()` returning a constant 62). So bottom copper always reports 63 regardless of how many inner layers the board actually has.

The board's own copper layer set is derived from its inner layer count (`libs/librepcb/core/project/board/board.cpp:363` onwards, exposed as `getCopperLayers()` at `libs/librepcb/core/project/board/board.h:142` and `getInnerLayerCount()` at `:141`). The dense mapping is therefore:

```
to_dense(layer, board) = layer.isBottom() ? board.getInnerLayerCount() + 1
                                          : layer.getCopperNumber()
from_dense(index, board) = Layer::copper(index == board.getInnerLayerCount() + 1
                                         ? Layer::innerCopperCount() + 1
                                         : index)
```

`Layer::copper(int)` (`libs/librepcb/core/types/layer.h:260`, implemented at `libs/librepcb/core/types/layer.cpp:388`) takes the sparse number, so `from_dense` has to translate the bottom case back. Copy Horizon's round trip assertion (note 05 section 5.9): assert `to_dense(from_dense(i)) == i` on every call in debug builds. Layer mapping bugs are silent and catastrophic.

`copper_layer_count` for the snapshot is `board.getInnerLayerCount() + 2`. The engine's `LayerMask` holds 64 layers (`src/item.rs`, `LayerMask::MAX_LAYER = 63`), which covers LibrePCB's maximum exactly.

Mirrored pads need no special handling in the mapping. `Layer::mirrored(int innerLayers)` (`libs/librepcb/core/types/layer.h:207`, implemented at `libs/librepcb/core/types/layer.cpp:59`) swaps top and bottom and reflects inner layer `i` to `innerLayers - i + 1`, but the snapshot never calls it: `BI_Pad::getGeometries()` (`libs/librepcb/core/project/board/items/bi_pad.h:141`) is already keyed by absolute board layer, with the pad's mirror state resolved (`libs/librepcb/core/project/board/items/bi_pad.cpp:503`). The mirror only matters when transforming the geometry paths, see section 1.7.

### 1.4 The i64 to i32 range check

LibrePCB's `Length` is `int64_t` nanometres (`libs/librepcb/core/types/length.h:82`, accessor at `:96`). The engine is `i32` nanometres by `DESIGN.md` section 2, about plus or minus 2.1 metres. Note 05 section 7.4 chose "adopt i32 and reject out of range input at the snapshot boundary" as the lower risk option, and that stands.

The check belongs on the C++ side of the FFI, in the snapshot builder, not inside Rust, so the error can be reported as a LibrePCB `RuntimeError` with a board item to point at. Concretely: a helper `std::optional<int32_t> toEngineCoord(const Length&)` that fails outside `[-2000000000, 2000000000]`, chosen a little inside `INT32_MAX` so that a hull inflation near the edge does not wrap. A board with any copper outside that box refuses to start the router with a message naming the offending item, which is a better failure than a silent wrap. In practice the limit is 2 metres of board, so this fires only for corrupt or fixture data.

Note that the check must run on *inflated* extents, not raw coordinates: the spatial index inflates every query by `max_clearance` (`DESIGN.md` section 4.3), and hulls inflate further. Rejecting at 2.0 metres rather than 2.147 metres gives 147 mm of headroom, which is more than any clearance rule.

### 1.5 HostId assignment

`HostId` is an opaque `u64` the crate never interprets (`src/item.rs`, the `HostId` newtype). The host owns the meaning.

Use a per snapshot counter and a C++ side `std::vector<HostRef>` indexed by it, where `HostRef` is the typed parent handle Horizon invented (note 05 section 5.2) and the 2018 branch already reimplemented for LibrePCB (`git show upstream/add-pns-router:libs/librepcb/projecteditor/boardeditor/pns_router/pns_librepcb_iface.h`, the `PNS_LIBREPCB_PARENT_ITEM` class with four nullable pointers). Keep the typed shape, drop the `std::set` and the `operator<`: the 2018 version interned parents through a set lookup per item, which makes the sync quadratic exactly as Horizon's `std::list` scan does (note 05 section 5.9).

```cpp
struct HostRef {
  BI_NetLine* netLine = nullptr;
  BI_Via* via = nullptr;
  BI_Pad* pad = nullptr;
  BI_Hole* hole = nullptr;
  BI_Polygon* polygon = nullptr;   // board outline and copper polygons
  const Layer* layer = nullptr;    // which per layer solid of a pad this is
};
```

One host object gets exactly one `HostId` even when it becomes several engine items: a pad yields one solid per copper layer (section 1.7) and they all carry the pad's id, which is what `HostIndex`'s one to many host to engine direction is for (`src/snapshot.rs`, the `HostIndex` doc comment). So the `HostRef` needs no layer field for identity. Keep the layer anyway as a debugging aid on the reverse lookup, or drop it; nothing in the commit applier needs it, because the applier speaks in host objects and lets the engine resolve which of an object's items it collided with.

The 2018 branch carried `BI_Footprint` plus `BI_FootprintPad` because a pad had no identity independent of its placement; today `BI_Pad` covers both footprint pads and standalone board pads (`libs/librepcb/core/project/board/items/bi_pad.h:49`, two constructors at `:91` and `:101`), so one pointer suffices.

Ids are assigned in sync order starting at 1, so `HostId(0)` stays unused and can serve as a null in any C struct that needs one. The vector is cleared and rebuilt on every sync, so a `HostId` from a previous session is meaningless. Guard that with a session generation counter folded into the high bits if it ever becomes a debugging problem.

Pointers into the board are safe for the lifetime of one routing session only because the tool blocks other editors while active (`BoardEditorState_DrawTrace` calls `abortBlockingToolsInOtherEditors()` at the top of `startPositioning`, `libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:470`). The new tool must do the same.

### 1.6 Net ids

`NetId` is a `u32` newtype and "no net" is `Option::None`, not a reserved value (`src/item.rs`, the `NetId` doc comment). This removes Horizon's zero sentinel bug (note 05 section 5.5), so the host is free to number from zero. `None` means a non conductive obstacle: its clearance always applies and it is never "same net" with anything, which is why the engine asks a host to give copper a `NetId` even when the copper has no net of its own. See below for how far this integration goes on that.

The snapshot builder walks `board.getProject().getCircuit().getNetClasses()` and the board's net segments, interning `NetSignal` identity (`libs/librepcb/core/project/circuit/netsignal.h:62` for the uuid, `:65` for the net class) into a dense `u32` with a `QHash<const NetSignal*, uint32_t>` and a reverse `QVector<NetSignal*>`. `BoardDesignRuleCheckData` does the same walk for the DRC (`libs/librepcb/core/project/board/drc/boarddesignrulecheckdata.cpp:101` for the net class loop, `:111` for the segments), which is worth reading as the reference implementation for a board snapshot in this code base: it is a plain data structure copied out of the board for a separate consumer, exactly what we are building.

A pad or a net segment with no net signal gets `None`, which the FFI spells as net zero. That is a deliberate simplification and not the same thing KiCad does: KiCad hands the board's unconnected `NETINFO_ITEM` straight through (`pcbnew/router/pns_kicad_iface.cpp:1691`), so two unassigned pads read as the same net there and keep no clearance from each other, while here they collide like any two obstacles. Interning a net for unassigned copper would close it, and needs the C++ side to send an id instead of zero. Note that `BoardEditorState_DrawTrace` refuses to start a trace on a pad with no net at all (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:490` builds the exception, thrown at `:542`); the new tool inherits that restriction for now.

`RuleResolver::net_code` must return a positive integer for a real net, because the engine's topology code treats zero and below as "no net" (`src/rules.rs`, the `net_code` doc comment). Return `net.0 + 1`.

`RuleResolver::orphaned_net` is the net a route started in free space is placed on, the port of KiCad's `GetOrphanedNetHandle` (`pcbnew/router/pns_kicad_iface.cpp:3020`). It has to be stable, its net code has to be zero or below, and it must not be a net any board item carries, or a route in free space would stop keeping clearance from that net's copper. `NetId(u32::MAX)` with `net_code` answering `-1` for it satisfies all three: the interner numbers densely from zero, so the top of the range is unreachable.

### 1.7 Pad geometry

This is the part where LibrePCB is *better* shaped than KiCad, and the design should exploit it rather than copy KiCad's workaround.

KiCad syncs one always flashed shape per pad and defers the per layer question to `IsFlashedOnLayer` (note 05 section 3.4, the comment quoted there). LibrePCB has already resolved it: `BI_Pad::getGeometries()` returns a `QHash<const Layer*, QList<PadGeometry>>` (`libs/librepcb/core/project/board/items/bi_pad.h:141`), computed over the board's copper layers plus the mask layers (`libs/librepcb/core/project/board/items/bi_pad.cpp:503`). `getGeometryOnCopperLayer` (`libs/librepcb/core/project/board/items/bi_pad.cpp:613`) already decides full shape versus auto annular ring versus minimal annular ring from the design rules and from whether a trace is connected on that layer, and returns an empty list for a layer where the pad has no copper at all.

So the snapshot emits **one `Solid` per (pad, copper layer) pair with a non empty geometry list**, and `flashed_layers` is left `None`, which the engine reads as "the mask equals the layer span", here `LayerRange::single(dense_index)`. `IsFlashedOnLayer` is thereby a non issue for LibrePCB, which is what note 05 section 7.3 hoped for, but for a better reason than "v1 does not model it": LibrePCB genuinely materialises per layer copper.

The geometry itself converts as follows. `PadGeometry::toOutlines()` (`libs/librepcb/core/geometry/padgeometry.h:72`) gives a `QVector<Path>` in the pad's local frame. Transform it with `Transform(pad.getPosition(), pad.getRotation(), pad.getMirrored())`, which is exactly the recipe the DRC uses (`libs/librepcb/core/project/board/drc/boarddesignrulecheck.cpp:1593`). A `Path` may carry arcs, since its vertices have angles (`libs/librepcb/core/geometry/path.h:81` for the vertices, `:73` for `isCurved()`); flatten them with `Path::flattenedArcs(maxTolerance)` (`libs/librepcb/core/geometry/path.h:108`) using the same 5000 nm tolerance `PadGeometry` uses internally for planes, so the router and the plane builder see the same polygon.

Prefer native shapes where the geometry is recognisable rather than always emitting a polygon. `PadGeometry::getShape()` (`libs/librepcb/core/geometry/padgeometry.h:64`) is one of `RoundedRect`, `RoundedOctagon`, `Stroke`, `Custom`. A `RoundedRect` with zero corner radius maps to `Shape::Rect`; with equal width and height and a radius of half the side it maps to `Shape::Circle`; a `Stroke` with a single segment path maps to `Shape::Segment`, which is the engine's capsule. Everything else becomes a `Shape::Simple` polygon. A pad whose layer yields several geometries becomes several solids, each flagged `is_compound_shape_primitive` (`src/item.rs`, `ItemFlags`), and the engine's convex hull of the primitive hulls covers them together (`DESIGN.md` section 3).

Holes are their own engine items, per note 05 section 3.3 and `DESIGN.md` section 4.1. A `WorldItem` carries `hole: Option<Shape>` and `World::from_snapshot` drills it as a separate arena item attached to the solid, so the host does not build it directly. Each `PadHole` (`libs/librepcb/core/geometry/padhole.h:68` for the diameter, `:69` for the path, `:70` for `isSlot()`) becomes such a shape. A circular hole is a circle; a straight slot is a segment shape of the slot width; a curved or multi segment slot (`libs/librepcb/core/geometry/padhole.h:71`, `:72`) is flattened into a compound of segments.

**Attach the hole to exactly one of the pad's per layer solids, and give that one solid the full copper layer range.** A pad on a four layer board becomes up to four solids; if every one of them carried `hole: Some(...)` the world would end up with four coincident holes for one drill, and the hole to hole clearance rule would then report the pad colliding with itself. Emit the hole on the solid for the pad's component side layer, or, if that layer has no copper at all, as a standalone `WorldGeometry::Hole` item carrying the pad's host id. KiCad gives a pad's hole the full copper range regardless of the pad's own copper span, and this design keeps that.

`is_drilled_hole` answers true for a hole whose pad is plated, `is_non_plated_slot` answers true for a non round hole on a non plated pad.

A pad that is a non plated hole is not routable: clear `ItemFlags::routable` so the engine refuses to start a route on it, which is what KiCad's "cannot start routing from a non plated hole" does (note 05 section 3.4). LibrePCB expresses plating through `Pad::Function` and the pad's net, so the exact predicate is one of the open questions in section 6.

The per pad copper clearance override is `Pad::getCopperClearance()` (`libs/librepcb/core/geometry/pad.h:112`), reachable as `pad->getProperties().getCopperClearance()` (the DRC reads it that way at `libs/librepcb/core/project/board/drc/boarddesignrulecheckdata.cpp:90`). It is snapshotted per solid, feeds the rule resolver (section 2), and must be folded into `max_clearance`.

### 1.8 Vias

`BI_Via` gives position (`libs/librepcb/core/project/board/items/bi_via.h:68`), actual drill diameter (`:77`) and actual size (`:83`), where "actual" means after the auto sizing rules have been applied, which is what the DRC snapshots too (`libs/librepcb/core/project/board/drc/boarddesignrulecheckdata.cpp:148`). The copper span is `getVia().getStartLayer()` to `getVia().getEndLayer()` (`libs/librepcb/core/geometry/via.h:83`, `:84`), mapped through `to_dense`. The drill span is `BI_Via::getDrillLayerSpan()` (`libs/librepcb/core/project/board/items/bi_via.h:92`) when it is set, otherwise the copper span.

A via is one `WorldGeometry::Via` carrying position, diameter, drill, via type and a free flag; the engine drills the hole itself in `World::add_via`, so the host does not fill `hole` for a via. The engine's `Via` carries `StackMode` and a per layer diameter (`src/item.rs`, `Via::diameter`); LibrePCB has a single diameter, so `StackMode::Normal` with one value. `ViaType` is `Through` when the span covers every copper layer and `BlindBuried` otherwise, matching Horizon's test (note 05 section 5.4). `Via::isBlind()` and `isBuried()` exist already (`libs/librepcb/core/geometry/via.h:96`, `:97`) if a nicer classification is wanted.

For v1 the router only ever *places* through vias, so `Sizes::via_layer_range` needs the layer pair covering the whole board. The crate's open item on this (see `TODO.md`, milestone 3 deferrals) is resolved from the host side by handing `Sizes` a layer pair of `(0, copper_layer_count - 1)`. Blind and buried vias remain out of scope, which is consistent with `PLAN.md`'s non goals.

### 1.9 Board outline, holes and copper graphics

The board outline is every `BI_Polygon` whose layer is `Layer::boardOutlines()`, plus every footprint polygon and circle on that layer, which is how `Board::calculateBoundingRect` collects it (`libs/librepcb/core/project/board/board.cpp:752` onwards, and note the transform through `Transform(*device)` at `:765`). `Layer::boardCutouts()` and `Layer::boardPlatedCutouts()` are also board edges (`Layer::isBoardEdge()` at `libs/librepcb/core/types/layer.h:162`) and should be treated the same.

Each edge of the flattened outline path becomes its own non routable `Solid` spanning every copper layer, a **zero width** `Shape::Segment` flagged as a compound primitive, all edges sharing one host id: the clearance comes entirely from the board clearance rule, not from the shape. That is what KiCad does for `Edge_Cuts` (`pcbnew/router/pns_kicad_iface.cpp:2047`, where `MakeEffectiveShapesWithLineEndings` on an unfilled shape yields one segment per edge and the compound flag is set when there is more than one). Not one `Shape::Simple` per outline, which this note first said and step 2 built: that shape is filled, the collision code takes a containment shortcut on any closed chain, and the whole board interior became an obstacle so that no route could start anywhere (found and fixed while building step 4). Do not follow Horizon's chain of 10 nm segments per layer either, which note 05 section 5.9 explicitly warns against because it multiplies the index size by the layer count.

Board level mechanical holes are `board.getHoles()` (`libs/librepcb/core/project/board/board.h:249`), each a `BoardHoleData` with a diameter and a path (`libs/librepcb/core/project/board/boardholedata.h:59`, `:60`), reachable through `BI_Hole::getData()` (`libs/librepcb/core/project/board/items/bi_hole.h:66`). A hole with no copper of its own is a bare `WorldGeometry::Hole` spanning every copper layer, which is the variant that exists for exactly this case (`src/snapshot.rs`, the `Hole` variant's doc comment).

Copper polygons (`board.getPolygons()` at `libs/librepcb/core/project/board/board.h:235`, filtered to `getData().getLayer().isCopper()`) become routable `Solid`s on their layer carrying their net if they have one. Stroke texts on copper (`board.getStrokeTexts()` at `:242`, paths at `libs/librepcb/core/project/board/items/bi_stroketext.h:77`) become non routable null net `Solid`s, one per stroke, flagged compound. Both are optional for the first working version; the acceptance test in section 5 does not need them.

### 1.10 What is not synced

Planes are not synced. `BI_Plane::getFragments()` (`libs/librepcb/core/project/board/items/bi_plane.h:103`) is the filled copper, and KiCad and Horizon both leave the equivalent out (note 05 sections 3.5 and 5.4). The router routes through a pour and the host rebuilds it afterwards, see section 4.7.

Air wires are not synced (`BI_AirWire`); the engine computes its own ratlines through `TOPOLOGY::LeadingRatLine`, which is still a stub in the crate (`src/placer/line_placer.rs`, `update_leading_ratline`, tracked in `TODO.md`).

Zones are not synced in v1. `BI_Zone` with the `Zone::Rule::NoCopper` rule (`libs/librepcb/core/geometry/zone.h:55`) is the natural keepout, and note 05 section 7.6 sketches triangulated non routable solids for it, but that needs `RuleResolver::is_keepout` and a triangulation, neither of which is on the critical path. Leaving them out means the router will happily route through a keepout, which the DRC then reports. Say so in the tool's status bar text.

Non copper layers, devices as such, stop mask, solder paste, silkscreen, courtyards and documentation are all invisible to the router, matching note 05 section 3.7.

## 2. The rule resolver on the Rust side

The resolver lives in rust-core, implements `pnsrouter::rules::RuleResolver`, and is a table lookup over values the snapshot carried across, exactly as note 05 section 7.5 works out. It never calls back into C++, which keeps the collision inner loop free of FFI transitions. This is the single most important structural decision in this section: Horizon's resolver calls into its rule engine per query and pays for it in the shove loop (note 05 section 5.3).

### 2.1 Values the snapshot must carry

Per board, from `BoardDesignRuleCheckSettings` (`libs/librepcb/core/project/board/drc/boarddesignrulechecksettings.h`): `getMinCopperCopperClearance()` (`:112`), `getMinCopperBoardClearance()` (`:115`), `getMinCopperNpthClearance()` (`:118`), `getMinDrillDrillClearance()` (`:121`), `getMinDrillBoardClearance()` (`:124`), `getMinCopperWidth()` (`:130`), `getMinPthDrillDiameter()` (`:139`). Reachable as `board.getDrcSettings()` (`libs/librepcb/core/project/board/board.h:113`).

Per board, from `BoardDesignRules` (`libs/librepcb/core/project/board/boarddesignrules.h`): `getDefaultTraceWidth()` (`:57`) and `getDefaultViaDrillDiameter()` (`:60`), plus `getViaAnnularRing()` (`:89`) if via diameter constraints are wanted. Reachable as `board.getDesignRules()` (`libs/librepcb/core/project/board/board.h:110`).

Per net class, from `NetClass` (`libs/librepcb/core/project/circuit/netclass.h`): `getMinCopperCopperClearance()` (`:69`), `getMinCopperWidth()` (`:72`), `getMinViaDrillDiameter()` (`:75`), and the optional defaults `getDefaultTraceWidth()` (`:63`) and `getDefaultViaDrill()` (`:66`).

Per net, the net class it belongs to (`NetSignal::getNetClass()` at `libs/librepcb/core/project/circuit/netsignal.h:65`). The snapshot carries a per net record holding a net class index, so the resolver can go from `NetId` to the three net class values in one array index.

Per pad, the copper clearance override (section 1.7). Carried on the solid, not in a side table, so the resolver reads it off the `ItemRef`.

### 2.2 The combination rule

LibrePCB already combines a net class value with the board setting by `std::max`, in the DRC's helper methods: `getMinCopperCopperClearance` (`libs/librepcb/core/project/board/drc/boarddesignrulecheckdata.h:212`), `getMinCopperWidth` (`:224`) and `getMinViaDrillDiameter` (`:234`). The resolver must produce the same answers as the DRC or the router will produce boards that fail their own check.

The clearance ladder, following the shape of `FixedClearance` in `src/rules.rs` and KiCad's own maximum taking loop:

```
clearance(a, b):
  result = None
  if a and b are both holes:
      result = max(result, board.minDrillDrillClearance)
  if exactly one of a, b is a hole and the nets differ:
      result = max(result, board.minCopperNpthClearance)      # hole to copper
  if neither is a hole, the nets differ, and neither is a free pad:
      result = max(result,
                   max over both sides of
                     max(board.minCopperCopperClearance,
                         netclass(side).minCopperCopperClearance,
                         pad_override(side)))
  if either side is a board edge item:
      result = max(result, board.minCopperBoardClearance)
      if the other side is a hole: max(result, board.minDrillBoardClearance)
  return result
```

There is no `else` between the hole rules and the copper rule, deliberately: KiCad's comment "No 'else'; plated holes get both HOLE_CLEARANCE and CLEARANCE" is quoted in `src/rules.rs` and the port already reproduces it.

`clearance_epsilon()` returns zero. LibrePCB has no DRC epsilon, and note 05 section 7.5 records that this makes the router marginally stricter than KiCad, which is the safe direction.

`constraint()` answers seven of the thirteen types (`src/rules.rs`, `ConstraintType`): `Clearance` from the table above, `Width` from `max(board.minCopperWidth, netclass.minCopperWidth)` with `opt` from the net class default trace width or the board default, `ViaHole` from `max(board.minPthDrillDiameter, netclass.minViaDrillDiameter)` with `opt` from the net class default via drill or the board default, `ViaDiameter` from the via annular ring rule, `EdgeClearance` from `minCopperBoardClearance`, `HoleClearance` from `minCopperNpthClearance`, `HoleToHole` from `minDrillDrillClearance`. The other six are differential pair, tuning and physical clearance concepts LibrePCB does not have, and return `None`. Nothing in the routing core calls `constraint()` today (`src/rules.rs` says so in the method doc), so this can be written last.

`is_keepout` returns `Keepout::None` until zones are synced. `has_user_defined_physical_constraint` returns false, which keeps the collision ladder on its fast path.

### 2.3 max_clearance

`max_clearance` is a soundness parameter, not a hint: the spatial index stores un inflated boxes and every query inflates by it, so understating it silently drops obstacles (`DESIGN.md` section 4.3 and the log entry of 2026-09-08 on the index). Compute it as

```
max_clearance = max(board.minCopperCopperClearance,
                    board.minCopperBoardClearance,
                    board.minCopperNpthClearance,
                    board.minDrillDrillClearance,
                    board.minDrillBoardClearance,
                    max over every net class of minCopperCopperClearance,
                    max over every pad of copperClearance)
```

taking every net class in the circuit rather than only the ones in use, because a net class can be assigned mid session. Do **not** copy Horizon's blanket factor of four (note 05 section 5.4): it is an unexplained margin that costs broad phase performance. The maximum above is exact by construction, given that the resolver only ever returns a maximum over those same inputs. Add an assertion in the resolver that no answer exceeds `max_clearance`, which turns a future rule addition into a test failure rather than a routing corruption.

## 3. Driving the session from C++

### 3.1 Session lifetime and the FFI surface

The wrapper class, call it `BoardPnsRouter`, owns a `RustHandle<rs::PnsRouter>`. It is constructed on tool entry, destroyed on tool exit, and re-syncs its snapshot whenever the board changed underneath it. `BoardEditorState_DrawTrace` has the same shape: it takes over the undo stack for the duration and blocks other editors (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:470`).

As built (step 4) it lives in `libs/librepcb/core/project/board/boardpnsrouter.{h,cpp}`, not in the editor library as this note first said. It has no user interface, no graphics items and no undo stack, and it belongs next to `BoardPnsSnapshot`, which landed in core after this note was written and which it owns.

The FFI mirrors the crate's session facade (`DESIGN.md` section 7, `src/router.rs`):

| Tool event | `Router` method | Returns |
| --- | --- | --- |
| tool entry, board changed | rebuild snapshot, `Router::new` | session handle |
| hover, before the first click | `hover(at, layer)` | item ids for the status bar |
| left click, idle | `start_routing(at, start_item, layer, sizes)` | `PreviewFrame` |
| mouse move while routing | `move_to(at, end_item)` | `PreviewFrame` |
| left click while routing | `fix_route(at, end_item, force_finish)` | `FixOutcome` |
| backspace | `undo_last_segment()` | new end point |
| layer key, layer combo box | `switch_layer(layer)` | bool |
| via key | `toggle_via()` | |
| posture key | `flip_posture()` | |
| double click, or `fix_route` reporting finished | `finish()` | `CommitDiff` |
| escape | `stop()` | `CommitDiff` |

`PreviewFrame` and `CommitDiff` cross back through accessor functions, because they are read once and dropped and an out parameter protocol for variable length results would be worse. They are **not** separate handles, which is the one place the sketch above was changed: the session keeps its latest frame and its latest commit inside itself and C++ reads them right after the call that produced them. One handle type, one deleter, no lifetime for the host to get wrong, and a `PreviewFrame` is replaced on every event anyway.

### 3.1.1 What the FFI actually is

The prefix is `ffi_pnsrouter_*` throughout, matching the snapshot half of the module, and every function is the thinnest possible shim over the `Router` method of the same name. The whole surface, as of step 4:

- Session: `ffi_pnsrouter_new`, `_delete`, `_copper_layer_count`, `_routing_in_progress`, `_set_settings`, `_current_layer`, `_placing_via`.
- Events: `ffi_pnsrouter_hover`, `_hover_at`, `_is_starting_point_routable`, `_start_routing`, `_move_to`, `_fix_route`, `_finish`, `_undo_last_segment`, `_switch_layer`, `_toggle_via_placement`, `_flip_posture`, `_toggle_corner_mode`, `_stop_routing`, `_abort_routing`.
- Preview readback: `ffi_pnsrouter_preview_item_count`, `_preview_item`, `_preview_item_point`, `_preview_has_via`, `_preview_via`, `_preview_fixed_via_count`, `_preview_fixed_via`, `_preview_ratline_point_count`, `_preview_ratline_point`, `_preview_violation_count`, `_preview_violation`, `_preview_hidden_count`, `_preview_hidden_at`.
- Commit readback: `ffi_pnsrouter_commit_removed_count`, `_removed_at`, `_added_count`, `_added_at`, `_updated_count`, `_updated_at`.

`continue_from_end`, `nearest_ratsnest_anchor`, `assign_host_ids`, `set_ortho_mode`, the recorder and the debug decorator are deliberately absent; they belong to later steps.

The conventions the sketch left open, decided while building it:

- `hover` stores its answer in the session and hands it back with a count and an index accessor, rather than filling a caller allocated buffer. It is then the same shape as every other variable length answer on this boundary, and there is no capacity to get wrong and no truncation case to document. It answers host ids, because host ids are what every other method takes.
- `StartError` becomes `PnsStartResult`, a flat enum with `Ok` first. The host id and the item id its two naming variants carry are dropped: the host already knows which object it asked about, and an engine item id means nothing to it.
- `FixOutcome` becomes `PnsFixOutcome` with a third value, `NotRouting`, which is what `Router::finish`'s `None` turns into.
- New enums are `#[repr(C)]` like the snapshot half's `PnsShapeKind` and `PnsViaType`, and are carried as typed fields rather than as bare integers. Each variant's doc comment names the crate variant it maps to. `pnsrouter::item::ViaType` has five values and `PnsViaType` has three, so a micro via reports as blind and the unset value reports as a through via.
- Optional values use the negative sentinel the snapshot half already uses: a clearance of `-1` is "no rule applies", a layer index of `-1` is "no layer", a host id of `0` is "no object".
- A net crosses as the snapshot's number, counted from one with zero for "no net". The engine's orphan net, `NetId(u32::MAX)`, is the one net the host never sent, so it reads back as zero too and `BoardPnsRouter` turns it into a null `NetSignal`, which is what a route placed in free space gets.
- A cursor point is clamped to the engine's coordinate range rather than rejected. The snapshot builder rejects an out of range coordinate so that the host can name the offending board item; a cursor is not a board object and there is nothing to name.
- `ffi_pnsrouter_set_settings` and `ffi_pnsrouter_new` derive `RoutingSettings` and `Sizes` through one shared helper, so a session created with a set of values and a session updated to it are the same session. The update starts from the session's current settings rather than from the defaults, so a corner mode the user cycled survives a width change.
- The session replaces its stored frame on exactly the calls the crate returns one from, which is `start_routing`, `move_to`, `fix_route` and `finish`, plus the two that end a session. The small commands (`switch_layer`, `toggle_via_placement`, `flip_posture`, `toggle_corner_mode`) return no frame, so the stored one is left alone and the host follows them with a move, which is what KiCad's host does anyway. The same applies after a fix: it clears the placer's head, so anything that reads the placement has to move first.

Escape does **not** discard the route. Both KiCad and Horizon keep the already fixed segments on escape, and note 05 section 5.7 argues from the fact that two independent code bases agree that this is inherent to the router's design rather than a KiCad quirk. LibrePCB's own draw trace tool disagrees (escape aborts the command group, `libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:129` into `abortPositioning`), so this is a deliberate behavioural difference between the two tools and belongs in the open questions of section 6.

### 3.2 Cursor snapping stays on the C++ side

The crate takes already snapped points; snapping is host work (`DESIGN.md` section 7). Note 05 section 4.5 records KiCad's invariant that every `Move` call receives the snapped point and that the visible crosshair is forced to the same coordinate. Preserve it.

LibrePCB's snapping machinery is `BoardEditorState::findItemsAtPos` (`libs/librepcb/editor/project/board/fsm/boardeditorstate.h:202`, implemented at `libs/librepcb/editor/project/board/fsm/boardeditorstate.cpp:155`) with the `FindFlag` set (`libs/librepcb/editor/project/board/fsm/boardeditorstate.h:67`). Its priority table is documented in a long comment at `libs/librepcb/editor/project/board/fsm/boardeditorstate.cpp:171` and is close enough to KiCad's five slot scheme (note 05 section 4.2) that reimplementing KiCad's would be wrong: vias beat pads beat netpoints beat netlines, current layer beats other layers, and near matches and next grid matches are demoted by fixed offsets. Use it as it stands.

The draw trace tool's own call sites are the template. The start anchor search uses `FindFlag::Vias | NetPoints | NetLines | BoardPads | FootprintPads | AcceptNextGridMatch` (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:512`); the end anchor search restricts to the current layer and the current net signal and excludes the items being placed (`:681`). The new tool does the same, then maps the found `BI_*` to a `HostId` through the reverse lookup of section 1.5 and hands the engine `(snapped point, host id)`.

Shift disables snapping in the existing tool (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:143` and `:160`, with a re-read of the modifier on every mouse move at `:177` to survive lost focus events). Keep the same gesture, and keep the re-read: it is a real robustness fix, not an accident.

The grid interval is `getGridInterval()` (`libs/librepcb/editor/project/board/fsm/boardeditorstate.h:195`) and the snapped point is `pos.mappedToGrid(getGridInterval())`, which is what `startPositioning` does at `libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:472`.

Make it structurally impossible to hand the engine an unsnapped point. Note 05 section 4.5 suggests a `SnappedPoint` newtype; on the C++ side the equivalent is that the wrapper's `move`, `start` and `fix` take a small `struct SnappedCursor { Point pos; std::optional<HostId> item; }` produced by exactly one private method.

### 3.3 Preview readback

`PreviewFrame` is a whole frame replacement (`DESIGN.md` section 7): the host clears its preview items and rebuilds them on every event. That matches KiCad's actual semantics, where `EraseView` runs at the top of every move (note 05 section 7.2).

LibrePCB's board editor has **no existing tool that renders without editing the document**, which is the second largest risk in this integration. Every other board tool, draw trace included, opens a command group and edits real board items so that the normal `BGI_*` graphics items render them (see `SubState_PositioningNetPoint` and its comment "in this state, an undo command is active!" at `libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.h:137`). The `BGI_*` items cannot be reused because each is bound to a board item by reference (`BGI_NetLine` holds a `BI_NetLine&`, `libs/librepcb/editor/project/board/graphicsitems/bgi_netline.h:87`).

The primitives that do fit are the same two the 2018 branch used: `PrimitivePathGraphicsItem` (`libs/librepcb/editor/graphics/primitivepathgraphicsitem.h:50`), which takes a `QPainterPath`, a line width and a line and fill layer, and `PrimitiveCircleGraphicsItem` (`libs/librepcb/editor/graphics/primitivecirclegraphicsitem.h:49`) for vias. `PrimitiveHoleGraphicsItem` (`libs/librepcb/editor/graphics/primitiveholegraphicsitem.h:54`) covers drills if wanted. Layers come from `GraphicsLayerList::get(const Layer&)` (`libs/librepcb/editor/graphics/graphicslayerlist.h:60`), which the FSM context already carries (`libs/librepcb/editor/project/board/fsm/boardeditorfsm.h:104`, the `layers` member). Items go into the scene with `GraphicsScene::addItem(QGraphicsItem&)` (`libs/librepcb/editor/graphics/graphicsscene.h:104`) and come out with `removeItem`.

Four styles are needed (note 05 section 4.11): head trace, hover, semi solid, collision. Only two matter for v1. The head trace is the line being placed, drawn on its copper layer at full saturation. A collision is drawn in a fixed colour; KiCad uses opaque green. `PrimitivePathGraphicsItem::setState` and `setLighterColorsWithMinAlpha` (`libs/librepcb/editor/graphics/primitivepathgraphicsitem.h:81`, `:82`) give enough control without inventing a new graphics item class.

Rebuilding every preview item on every mouse move will allocate. If profiling says it matters, pool the path items by index and only reset their paths, which is a local optimisation inside the preview renderer and changes no interface.

The clearance halo (KiCad draws the geometry twice, once inflated, note 05 section 4.11) is optional for v1 and is the natural second increment.

### 3.4 Toolbar and keyboard

The board editor's tool UI is Slint, driven through a fixed set of generic per tab properties. `DrawTraceToolBar` (`libs/librepcb/ui/project/board/drawtracetoolbar.slint:16`) is a horizontal layout of a layer combo box bound to `tool-layer` (`:23`), a trace width `LengthEdit` bound to `tool-line-width` with `tool-filled` reused as its auto flag (`:33`), a via drill edit bound to `tool-drill` with `tool-pressfit` as its auto flag (`:96`), a via size edit bound to `tool-size` with `tool-mirrored` as its auto flag (`:159`), and a wire mode selector bound to `tool-wire-mode` (`:192`). The toolbar is selected by `tabs[index].tool == EditorTool.wire` (`libs/librepcb/ui/project/board/board2dtab.slint:131`), where `EditorTool` is the enum at `libs/librepcb/ui/api/types.slint:350`.

The C++ side of that binding is `Board2dTab::fsmToolEnter(BoardEditorState_DrawTrace&)` (`libs/librepcb/editor/project/board/board2dtab.cpp:1275`), which connects each tool property to a signal and slot pair on the state and fills `mToolLayers` from `state.getAvailableLayers()`. Menu actions in the toolbar go through `TabAction` values (`libs/librepcb/ui/api/types.slint:871` for `toolbar-trace-width-save-in-board`) dispatched in a switch at `libs/librepcb/editor/project/board/board2dtab.cpp:1021`.

The interactive router needs more controls than the existing toolbar has: routing mode (mark obstacles, walkaround, shove), corner mode, posture flip and a via toggle in addition to layer, width, via size and via drill. Three of those have no generic tool property today. The cheapest honest approach is a new `InteractiveRouteToolBar` Slint component that reuses `tool-layer`, `tool-line-width`, `tool-drill` and `tool-size`, and adds new per tab properties for mode and corner mode, plus a new `EditorTool` value. That means touching `libs/librepcb/ui/api/types.slint`, which is a shared UI contract, so it is worth agreeing with upstream first (section 6).

Keyboard commands come from `EditorCommandSet` (`libs/librepcb/editor/editorcommandset.h`), which is where the tool shortcut lives (`toolTrace` at `:1183`, bound to `W`). Reuse `layerUp` and `layerDown` (`:1267`, `:1276`, bound to PageUp and PageDown) for the layer switch, which is the gesture KiCad users expect. A new command is needed for the via toggle, for undo last segment (Backspace, which has no command today), for cycling the routing mode and for flipping the posture. The wire mode commands (`wireModeHV` at `:1420` and its four siblings) are the model for how a mode cycle is registered. The existing draw trace tool cycles wire mode on a right click while routing (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:223`), which is a precedent for binding posture flip to the same gesture.

### 3.5 Where the new state sits in the FSM

Add `BoardEditorState_RouteTrace` (name proposal; alternatives are `_DrawTraceInteractive` from `doc/work/006`, which is long, and `_PushAndShove`, which names the implementation rather than the tool). It derives from `BoardEditorState` (`libs/librepcb/editor/project/board/fsm/boardeditorstate.h:61`) and lives next to the existing tool in `libs/librepcb/editor/project/board/fsm/`.

Three edits wire it in. A new enum value `ROUTE_TRACE` in `BoardEditorFsm::State` (`libs/librepcb/editor/project/board/fsm/boardeditorfsm.h:93`, next to `DRAW_TRACE`), a registration line in the constructor (`libs/librepcb/editor/project/board/fsm/boardeditorfsm.cpp:96`, next to the draw trace line), and a `processRouteTrace()` entry point next to `processDrawTrace()` (`libs/librepcb/editor/project/board/fsm/boardeditorfsm.cpp:187`).

## 4. The commit applier

### 4.1 The shape of the problem

The engine hands back a `CommitDiff` of removed host ids, added items and updated items whose identity it preserved (`DESIGN.md` section 7). The added items are **free floating segments and vias**: a segment is two points, a width and a layer, with no notion of a junction, and the engine has no idea what a `BI_NetSegment` is.

LibrePCB requires every trace to live inside a `BI_NetSegment` (`libs/librepcb/core/project/board/items/bi_netsegment.h:53`) and to run between two `BI_NetLineAnchor`s (`libs/librepcb/core/project/board/items/bi_netline.h:46`), which is one of `BI_NetPoint`, `BI_Via` or `BI_Pad`. So the applier's job is to reconstruct topology from geometry.

### 4.2 One undo command group per route

The whole route is one undo entry, not one per fixed segment. Note 05 section 4.9 establishes this for KiCad and argues it maps cleanly onto LibrePCB.

The applier is therefore a single `UndoCommandGroup`, `CmdBoardApplyPnsCommit` (`libs/librepcb/editor/project/cmd/cmdboardapplypnscommit.{h,cpp}`), constructed with the board and the commit and handed to `UndoStack::execCmd` (`libs/librepcb/editor/undostack.h:214`). It builds and executes its children inside its own `performExecute()` with `UndoCommandGroup::execNewChildCmd` (`libs/librepcb/editor/undocommandgroup.h:106`, implemented at `libs/librepcb/editor/undocommandgroup.cpp:129`), which executes each child as it is appended. That is exactly the property section 4.3 needs, and it is why the applier does not use the stack's own `beginCmdGroup` (`libs/librepcb/editor/undostack.h:227`) / `appendToCmdGroup` (`:244`) / `commitCmdGroup` (`:255`) sequence: a command object is self contained and testable without a stack, while the group opened on the stack is what the interactive tool needs when it wants the board half edited between events.

Note the difference from the existing draw trace tool, which opens the group at the *start* of the route (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:478`) and keeps the board in a half edited state throughout. The router tool holds no group while routing, because the preview lives outside the document.

### 4.3 Anchor resolution happens at apply time, not while buffering

This is Horizon's trap, note 05 section 5.6 finding 9. Horizon resolves each new segment's endpoints against the live board inside `AddItem`, scanning for a coincident pad and then a coincident junction and creating one if neither is found. A host that buffers those callbacks into a command group and applies them later would have every lookup miss, because the buffered writes are not visible to the buffered reads.

The crate avoids the trap by construction: it returns a diff instead of calling back. But the applier can reintroduce the same bug if it resolves anchors against the board while building the command objects rather than while executing them, because `CmdBoardNetSegmentAddElements::addNetPoint` returns the `BI_NetPoint*` immediately but the point is only added to the board when the command executes.

`CmdBoardApplyPnsCommit` does everything in `performExecute()` and appends each child with `execNewChildCmd`, so an endpoint is resolved against the board as it stands at that moment and sees every net point, via and split point an earlier endpoint added. `execNewChildCmd` refuses to run once the group itself was executed, but `UndoCommand::execute` only increments `mRedoCount` *after* `performExecute()` returns (`libs/librepcb/editor/undocommand.cpp:58`, with `wasEverExecuted()` reading that counter at `libs/librepcb/editor/undocommand.h:63`), so a group is free to build itself from inside its own execute. `CmdRemoveBoardItems` and `CmdBoardSpecctraImport` are both written that way.

### 4.4 The algorithm

The order is: move the vias that only moved, remove everything else the router superseded, then add, then simplify.

**Vias the router shoved.** `CmdBoardViaEdit::setPosition` (`libs/librepcb/editor/project/cmd/cmdboardviaedit.h:57`) moves a via in place and preserves its identity, which is worth doing because a via's uuid appears in the file format. This runs *before* the removals, not after: removing anything from a net segment re-creates the whole segment (see below), and the moved via has to carry its new position into that copy. A via whose layer span changed, and every updated net line, is a removal plus an addition instead, because `CmdBoardNetLineEdit` can change layer and width (`libs/librepcb/editor/project/cmd/cmdboardnetlineedit.h:58`, `:59`) but not the endpoints.

**Removals.** Not `CmdBoardNetSegmentRemoveElements` (`libs/librepcb/editor/project/cmd/cmdboardnetsegmentremoveelements.h:58` onwards). That command is unusable on its own here, because `BI_NetSegment::removeElements` requires the segment to be cohesive again by the time the command returns (`libs/librepcb/core/project/board/items/bi_netsegment.cpp:282`, calling `areAllNetPointsConnectedTogether()` at `:401`), and removing a net line out of the middle of a trace splits its segment in two, while removing one off the end leaves its former corner unreachable. Both throw a `LogicError`.

Use `CmdRemoveBoardItems` (`libs/librepcb/editor/project/cmd/cmdremoveboarditems.h:89` for `removeVias`, `:97` for `removeNetLines`) instead. Its `removeNetSegmentItems` (`libs/librepcb/editor/project/cmd/cmdremoveboarditems.cpp:176`) feeds what is left into `BoardNetSegmentSplitter`, removes the whole net segment and re-creates one segment per connected component, dropping junctions nothing reaches. It is the reference implementation for removing net objects in this code base. Its `getModifiedNetSegments()` (`libs/librepcb/editor/project/cmd/cmdremoveboarditems.h:123`) hands back the segments that survived, which is what the simplification pass at the end needs. The price is that every pointer into an affected net segment is stale afterwards, including the `BI_NetLine*` and `BI_NetPoint*` of items that were *not* removed, so the removals have to come before any anchor lookup.

**Anchor resolution.** For every endpoint of every added segment, in this order of preference.

If the point coincides with an existing `BI_Pad`, `BI_Via` or `BI_NetPoint` of the same net on that layer, that item is the anchor. `findItemsAtPos`, which the draw trace tool uses for this (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:681`), is a method of `BoardEditorState` and needs a `BoardGraphicsScene`, so a command cannot call it. Walk the board instead: `Board::getDeviceInstances()` (`libs/librepcb/core/project/board/board.h:206`) for footprint pads and `Board::getNetSegments()` (`:214`) for board pads, vias and net points, both of them `QMap`s and therefore deterministically ordered. That is not a workaround: the scene query exists for the fuzzy "next grid match" behaviour an interactive tool wants, while the router's endpoints are exact by construction, so an exact comparison is both correct and cheaper.

If the point lies in the interior of an existing `BI_NetLine` of the same net on that layer, split it. `CmdBoardSplitNetLine(netline, pos)` (`libs/librepcb/editor/project/cmd/cmdboardsplitnetline.h:55`) creates the point and rewires the two halves, and `getSplitPoint()` (`:58`) returns the new `BI_NetPoint`. The point is created in the constructor (`libs/librepcb/editor/project/cmd/cmdboardsplitnetline.cpp:44`), so it can be read before the command runs. "Interior" is `Toolbox::shortestDistanceBetweenPointAndLine` (`libs/librepcb/core/utils/toolbox.h:288`) being zero with the point not equal to either end. If the exactness of that ever becomes a problem the failure mode is benign: the endpoint becomes a new net point instead of a T junction, which the DRC then complains about rather than the applier throwing.

If the point is a via the engine placed, the anchor is that via, and this is where the via itself goes on the board. A via cannot be added to an existing net segment on its own, because `BI_NetSegment::addElements` runs the same cohesion check (`libs/librepcb/core/project/board/items/bi_netsegment.cpp:201`) and a via with no trace on it is not connected to the rest. So the applier holds the commit's vias back and adds each one inside the very `CmdBoardNetSegmentAddElements` that adds the first net line ending on it. A via nothing ends on gets a net segment of its own, which is cohesive because a segment holding a single via and nothing else is.

Otherwise create a net point with `CmdBoardNetSegmentAddElements::addNetPoint(pos)` (`libs/librepcb/editor/project/cmd/cmdboardnetsegmentaddelements.h:66`).

**Adding.** Every engine segment becomes a net line with `addNetLine(anchorA, anchorB, layer, width)` (`:68`) and every engine via a `BI_Via` with `addVia(const Via&)` (`:64`). The `Via` value carries position, layer span, drill and size, which is what `BI_Via` wraps (`libs/librepcb/core/project/board/items/bi_via.h:71`). Both endpoints and the net line go in as one command, again because of the cohesion check.

**No net.** A route started in free space carries no net signal. `BI_NetSegment` takes a nullable `NetSignal*` and documents it (`libs/librepcb/core/project/board/items/bi_netsegment.h:60` for the constructor, `:149` for the member comment), `CmdBoardNetSegmentAdd` takes the same nullable pointer (`libs/librepcb/editor/project/cmd/cmdboardnetsegmentadd.h:52`) and `BI_NetSegment::addToBoard` guards every net signal access. So the null passes straight through and needs no special case. Note that this is only about the board side: `BoardEditorState_DrawTrace` still refuses to *start* a trace on a pad with no net (section 1.6), and the router tool inherits that.

### 4.5 Merging net segments

A route that lands on an anchor belonging to a different `BI_NetSegment` merges the two. `CmdCombineBoardNetSegments(toBeRemoved, oldAnchor, result, newAnchor)` (`libs/librepcb/editor/project/cmd/cmdcombineboardnetsegments.h:54`) does it. It re-creates every item of `toBeRemoved` inside `result` as a *new* object with a new uuid, except `oldAnchor`, which is dropped and whose net lines are rewired onto `newAnchor` (`libs/librepcb/editor/project/cmd/cmdcombineboardnetsegments.cpp:74` onwards). Two things follow. `oldAnchor` has to be a `BI_NetPoint`, because dropping a via or a pad would lose it; the draw trace tool handles both directions of that constraint and skips the pair when neither side is a net point (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:796` and `:803`, with the `continue` at `:807`). And no pointer into `toBeRemoved` survives the call.

The applier arranges for the first constraint rather than testing for it, which is simpler than the tool's version and needs no `continue` case. Adding one net line involves at most one merge, at the far end only: the near end is what *chose* the net segment to add to, so it is either already in that segment or a footprint pad which belongs to no segment at all and can therefore anchor any of them. The far end, when its anchor lives in another segment, gets a fresh net point in the working segment as a stand in, and that net point is what is dissolved into the far anchor. The stand in is a net point by construction, so the merge always has something to dissolve.

A route that starts and ends inside the same net segment needs no merge, only the new lines.

Afterwards, run `CmdSimplifyBoardNetSegments` over the touched segments, as the existing tool does on abort (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:887`). It collapses redundant net points, which the engine's optimiser will otherwise leave behind at former corners. This runs inside the same group, so it is part of the one undo entry, and only over the segments that are still on the board, since a merge takes one of them off it.

### 4.6 What the 2018 attempt teaches

`upstream/add-pns-router` (tip 9cb664f55, "Wip", authored 2018-08-09) vendored Horizon's KiCad 6 era router and wrote `pns_librepcb_iface.cpp` against it. The world sync works: `syncNetLine`, `syncVia` and `syncPad` are complete and are essentially what section 1 describes, with pads polygonised through Clipper. `DisplayItem` works and uses `PrimitivePathGraphicsItem` and `PrimitiveCircleGraphicsItem`, which is the evidence that those two primitives are sufficient for a preview.

`AddItem` is entirely commented out, `RemoveItem` is entirely commented out, and `Commit()` is `EraseView()` and nothing else. The rule resolver returns a hard coded 0.1 mm. That is where the attempt stopped, and it stopped at exactly the piece section 4.4 describes. Treat that as the measurement of where the effort is: the sync is a day, the write back is the work.

### 4.7 Plane rebuild after commit

The applier does nothing here, because the item lifecycle already does it. `BI_NetLine::addToBoard` and `removeFromBoard` invalidate the line's own layer (`libs/librepcb/core/project/board/items/bi_netline.cpp:189` and `:210`), and `BI_Via::addToBoard`, `removeFromBoard` and `setPosition` invalidate all of them (`libs/librepcb/core/project/board/items/bi_via.cpp:164`, `:183` and `:120`). Every path the applier takes goes through those, on execute, on undo and on redo alike, so `Board::invalidatePlanes` (`libs/librepcb/core/project/board/board.h:224`, set taking overload at `:225`) never has to be called by hand.

What remains is starting the rebuild, which belongs to the tool rather than to the command: `BoardEditor::schedulePlanesRebuild()` (`libs/librepcb/editor/project/board/boardeditor.cpp:270`) starts the debounced timer that `startPlanesRebuild` (`:274`) drives through `BoardPlaneFragmentsBuilder`. Air wires rebuild themselves: the plane builder's completion handler calls `forceAirWiresRebuild()` (`libs/librepcb/editor/project/board/boardeditor.cpp:280`).

## 6. Open questions for upstream

These need answers from Urban Bruhin before the C++ is written, because each one can invalidate a chunk of the design. They are listed in the order they block work. Per `CONTRIBUTING.md:23` and the rules that follow it, any issue or forum post carrying these questions must be written by hand and must declare where an LLM was used; that section is explicit that LLM written issue and pull request text is unwelcome.

**Q1. Is a second trace tool acceptable, or must the router replace the existing one?** The design in section 3.5 adds `BoardEditorState_RouteTrace` next to `BoardEditorState_DrawTrace`. If upstream wants one tool with a mode switch instead, the FSM and toolbar work changes shape and the fallback path disappears.

**Q2. Is a new `EditorTool` value and new per tab tool properties in `libs/librepcb/ui/api/types.slint` acceptable?** The router needs routing mode, corner mode and posture controls that the generic tool property set does not have (`libs/librepcb/ui/api/types.slint:350` for the enum, and the `tool-*` properties the existing toolbars reuse). This is a shared UI contract and the answer determines whether the toolbar is a new component or an extension of `DrawTraceToolBar`.

**Q3. Should escape keep the fixed segments or discard the route?** KiCad and Horizon both keep them (note 05 sections 4.6 and 5.7); LibrePCB's draw trace tool discards (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:129`). Two established behaviours are in conflict and the answer is a product decision, not a technical one.

**Q4. What is the correct predicate for "this pad is a non plated hole"?** Section 1.7 needs it to clear `routable` so the router refuses to start there, the way KiCad does. LibrePCB expresses plating through `Pad::Function` (`libs/librepcb/core/geometry/pad.h:116`) and the pad's net rather than an explicit NPTH attribute, and reading the enum from outside is guesswork.

**Q5. Is it acceptable that the router routes through keepout zones in v1?** Zones are not synced (section 1.10), so a `BI_Zone` with `Zone::Rule::NoCopper` (`libs/librepcb/core/geometry/zone.h:55`) does not stop the router, and the DRC catches it afterwards. If that is unacceptable, zone triangulation and `RuleResolver::is_keepout` move onto the critical path.

**Q6. Should the crate be a Cargo git dependency during development or vendored?** rust-core currently takes only published crates (`libs/librepcb/rust-core/Cargo.toml:17` onwards) and the file carries a comment about pinning `zip` for maintenance reasons, so the project clearly has a view on dependency policy. A git dependency in a pull request may be a blocker even for review.

**Q7. Does the project want the router's preview to be a new graphics item class or is reuse of `PrimitivePathGraphicsItem` fine?** Section 3.3 reuses the primitives, which is what the 2018 branch did, but there is no existing tool that draws without editing the document, so there may be a house style for this that is not visible in the tree.

**Q8. What granularity of undo is wanted?** Section 4.2 makes the whole route one undo entry, following KiCad. The existing draw trace tool makes one entry per fixed segment pair, because it commits its command group on every click (`libs/librepcb/editor/project/board/fsm/boardeditorstate_drawtrace.cpp:836`). Users of the two tools would get different undo behaviour.

**Q9. Is `int32` nanometre coordinate range acceptable, given `Length` is `int64`?** Section 1.4 rejects any board with copper beyond about plus or minus 2 metres. That is far outside any real board, but it is a hard limit that LibrePCB does not otherwise have, and the refusal has to be a visible error rather than a silent clamp.

**Q10. Where should the C++ wrapper live?** Section 3.1 puts `BoardPnsRouter` in `libs/librepcb/editor/project/board/`, next to the FSM that drives it, because it touches the undo stack and the graphics scene. An argument exists for `libs/librepcb/core/project/board/` on the grounds that the snapshot builder only reads core types; splitting the snapshot builder into core and the session driver into editor is the compromise, and upstream's layering rules decide.
