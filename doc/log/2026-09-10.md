## Direction: close the gap with KiCad

Tags: #decision #plan

- The user wants feature parity with KiCad's router. Milestones 8 to 11 are added: the parallel obstacle query, dragging, differential pairs, meanders, in that order; arcs after them because they touch the geometry core everywhere. Work items 008 to 011.
- Determinism with threads: the parallel part only computes, the reduction ranks by (distance, uid), so answers are independent of thread count. Expected gain is bounded by the obstacle query's share of a move, about a fifth in the profile.
- Differential pairs need a host side pair identification; LibrePCB has none, so a naming convention is part of milestone 10. Meanders are chamfered only until arcs exist, which is also all LibrePCB can store.

## Decision: the parallel obstacle query ships off by default

Tags: #decision #performance #deviation

- Milestone 8 is implemented: `World::nearest_obstacle` cuts its candidate scan into blocks and runs them on `std::thread::scope`, which is KiCad's `pns_node.cpp:437` without a pool. The reduction stays sequential and ranks by (distance, uid), so the answer is independent of the thread count; `tests/parallelism.rs`, `tests/kicad_replay.rs` and two unit tests in `src/node.rs` pin that.
- `World::set_parallelism` defaults to **1**, which the work item asked to be `available_parallelism`. The measurement changed the answer. A `std::thread::scope` costs about 21 microseconds per block here, 42 for a two way split; scanning one obstacle candidate is about 2.2 microseconds; the queries big enough to be cut are 5% of them and carry a quarter of a scan that is 4% of a run. Eight interleaved runs on both boards show nothing better than the run to run spread and one thing reproducibly worse, the tail of mark obstacles mode, whose p95 rose 13 to 29% and whose worst move rose 25 to 32% across three separate batches.
- Root cause of the loss, and a deviation KiCad shares without paying for it: the candidate count does not predict the work. `hull_intersection` is hull segments times path segments, so a mode with short heads has cheap candidates, crosses the count threshold anyway and pays a thread for nothing. KiCad's dispatch to a warm pool is an order of magnitude cheaper than creating a thread, so it never notices.
- `MIN_CANDIDATES_PER_BLOCK` is 32 against KiCad's 8, for the same reason.
- `RuleResolver` keeps no `Send + Sync` bound. The parallel section never reaches the resolver (the clearance phase stays sequential, as KiCad's at `pns_node.cpp:346`), and a bound would stop a host from memoising behind a `RefCell` the way KiCad's own resolver does (`pns_kicad_iface.cpp:222`). If the boundary ever moves, the bound moves with it.

## Milestone 9, slice 2: the session facade and the post drag optimizer

Tags: #dragger #decision #deviation #kicad

- `Router::start_dragging(at, items, free_angle)`, drag branches in `move_to`, `fix_route`, `stop_routing` and `pending_update`, `RouterState::DragSegment` entered for the first time, and `SessionEvent::StartDragging { at, items, free_angle }` recorded, written, read and replayed. The event log's format version is unchanged: the grammar only gained a line, so every stored fixture still parses.
- **The note is wrong about `optimizeAndUpdateDraggedLine`.** Note 06 section 2.14 opens with "where every successful drag ends, in all three modes". Its five call sites are `pns_dragger.cpp:553`, `:757`, `:786`, `:857` and `:900`, all inside `dragViaWalkaround`, `dragWalkaround` and `dragShove`; `dragMarkObstacles` (`:381` to `:449`) never optimizes, which is what makes a mark obstacles drag follow the cursor exactly. The routine, `bestAnchorForPoint` and `pointHasBadCorner` are ported anyway, because every later slice's geometry ends in them, and the first two carry unit tests. `optimize_and_update_dragged_line` has an `#[expect(dead_code)]` rather than an `allow`, so the day the walkaround drag calls it the expectation itself becomes a warning.
- **`force_finish` carries KiCad's `aForceCommit` on the drag branch** instead of the fourth facade argument note 06 section 9.4 suggests. `ROUTER::FixRoute( aP, aEndItem, aForceFinish, aForceCommit )` drops one of the two on each branch (`pns_router.cpp:926`, `:930`), so no state gives both a meaning; taking one flag keeps every routing call site, the recorded `SessionEvent::FixRoute` and every stored fixture unchanged.
- **`stop_routing` commits nothing for a drag**, which is KiCad: `CommitRouting()` commits inside `if( m_state == ROUTE_TRACK )` only (`:960`) and `StopRouting` just tears down (`:967`). Only a fix commits a drag, through `DRAGGER::FixRoute`. So `Router::abort_routing` and `Router::stop_routing` do the same thing to a drag, and the crate's "escape commits" stance is a placement rule and not a drag rule.
- `DRAGGER::FixRoute` calls `ROUTER::CommitRouting( node )` through the dragger's router pointer, which this crate does not have. Split into `Dragger::fix_route_node`, everything up to the commit, and `Dragger::fix_route`, the whole of it; the facade uses the former so it can build the host facing `CommitDiff` before `World::commit` folds the node away and the handles go stale.
- **The dragged trace reaches the host with no head flag**, the open question of note 06 section 9.4. `moveDragging` sets no `PNS_HEAD_TRACE` where `movePlacing` sets it on every trace (`pns_router.cpp:656` against `:804`), and `dragMarkObstacles` adds the dragged line to the drag node, so it comes out of the node delta as ordinary settled geometry. Drawing it from `Traces()` as well would draw it twice.
- The KiCad log player takes `EVT_START_DRAG` now, mapping the event's uuids the way `EVT_START_ROUTE` maps its first one and passing `free_angle = false` for the literal `0` drag mode KiCad's player uses. All seven drag cases replay; six of them end with the dragged trace lying across something, because the mark obstacles fallback only reports what it runs into. Their tier 1 collision test and, for five of them, their tier 2 test are `#[ignore]`d with the measured numbers, which `doc/work/009-dragging.md` tabulates.

## Milestone 9, slice 5: multi drag

Tags: #dragger #decision #deviation #kicad #testing

- `src/multi_dragger.rs` holds `MULTI_DRAGGER` in full for a board without arcs: `MDRAG_LINE` minus its five dead fields, `Start`'s four phases, `Drag` with the `tryPosture` lambda over variants 0, 1 and 2, `multidragMarkObstacles` with `clipToOtherLine`, `multidragWalkaround` with its own `tryWalkaround` at a length limit factor of 3.0 against the single dragger's 30.0, `multidragShove` with the deliberate head order and the re-add block, `findNewLeaderSegment`, `restoreLeaderSegments` and the small members. `LineChain::point_along` (`shape_line_chain.cpp:2671`) is the one geometry routine the milestone genuinely added; `World::collide_lines` was already there from milestone 2 and is what `clipToOtherLine` needs.
- `SHOVE::ShoveMultiLines` does not exist in KiCad and nothing was added for it. Note 06 section 0 already said so and section 4 predicted the shove would need nothing: `clear_heads`, `add_head_line` once per line, `run`, `heads_modified`, `modified_head` and `current_node` are the whole call surface, and `ShovePolicy::DONT_OPTIMIZE` finally has its one user, which is the reason that flag exists in KiCad at all.
- **The one deviation is erratum E28.** `MDRAG_LINE::dragDist` is assigned only in the segment branch (`pns_multi_dragger.cpp:907`), so in corner mode every line compares equal under `compareDragStartDist` and `std::sort` (`:472`, `:629`) is not stable; the walkaround attempt order and the shove head order are therefore unspecified in KiCad, and both change the result. The port sorts by `(drag_dist, mdrag_index)`, so segment mode keeps KiCad's order and corner mode falls back to the order the host listed the selection in. `DESIGN.md` section 8.
- Errata E17 to E27 are transcribed with a comment each. The two worth naming: **E17**, `multidragWalkaround` storing the reverse attempt's walked lines under the forward attempt's indices (`:501` against `:513`), which scrambles `draggedLine` whenever the reverse order wins but leaves the node correct, so only `restoreLeaderSegments` sees it; and **E25**, `clipToOtherLine` installing an empty chain when every probe collides, whose other half, the `int` narrowing of the chain length at `:307`, cannot be inherited because `LineChain::length` and `point_along` are `i64` here.
- One repair that is not an erratum: KiCad's `preWalkNode` (`:475`) is a local that is never deleted, so a walkaround multi drag leaks one node per mouse move. It is a member here and is dropped at the top of the next drag, which takes `m_lastNode` with it.
- `Router::start_dragging` dispatches on the shape of the item set as `pns_router.cpp:176` to `:190` does, so `StartError::MultiDragUnsupported` is gone and `StartError::ComponentDragUnsupported` takes its place: all solids is a component drag and is still refused, more than one segment or arc is a multi drag, and everything else is the single dragger, which reads `aPrimitives[0]` and ignores the rest. A lone pad is therefore a component drag refusal now and not a `NotDraggable`, which is what KiCad does and what the old test had wrong. **The LibrePCB fork's `rust-core` maps `PnsStartResult::MultiDragUnsupported`, so bumping the submodule needs that enum renamed**; recorded in `SUGGESTIONS.md`.
- The two draggers meet in `router::ActiveDragger`, a private two variant enum with both variants boxed, not a trait. `DESIGN.md` section 11 and note 06 section 9.3 both asked for that, and it is why there is no `src/drag_algo.rs`.
- `Router::last_committed_leader_segments` and the new `Router::host_of` are the selection handoff `ROUTER_TOOL::performDragging` needs (`router_tool.cpp:3164`, `:3238`): the router deletes the segments the user had selected and makes new ones, so the host is handed the new ones and selects their parents. `World::commit` re homes items into the root rather than replacing them, so the ids stay valid across the fix.
- The KiCad log player takes `EVT_START_MULTIDRAG` now, sharing the branch it shares in KiCad (`qa/tools/pns/pns_log_player.cpp:155`). **No corpus case emits one** (note 05 section 6.9), so nothing was un-ignored and the eleven goldens are unchanged, `issue23449` included.
