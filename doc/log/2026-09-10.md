Tags: #decision #plan

## Decision: the parallel obstacle query ships off by default

Tags: #decision #performance #deviation

- Milestone 8 is implemented: `World::nearest_obstacle` cuts its candidate scan into blocks and runs them on `std::thread::scope`, which is KiCad's `pns_node.cpp:437` without a pool. The reduction stays sequential and ranks by (distance, uid), so the answer is independent of the thread count; `tests/parallelism.rs`, `tests/kicad_replay.rs` and two unit tests in `src/node.rs` pin that.
- `World::set_parallelism` defaults to **1**, which the work item asked to be `available_parallelism`. The measurement changed the answer. A `std::thread::scope` costs about 21 microseconds per block here, 42 for a two way split; scanning one obstacle candidate is about 2.2 microseconds; the queries big enough to be cut are 5% of them and carry a quarter of a scan that is 4% of a run. Eight interleaved runs on both boards show nothing better than the run to run spread and one thing reproducibly worse, the tail of mark obstacles mode, whose p95 rose 13 to 29% and whose worst move rose 25 to 32% across three separate batches.
- Root cause of the loss, and a deviation KiCad shares without paying for it: the candidate count does not predict the work. `hull_intersection` is hull segments times path segments, so a mode with short heads has cheap candidates, crosses the count threshold anyway and pays a thread for nothing. KiCad's dispatch to a warm pool is an order of magnitude cheaper than creating a thread, so it never notices.
- `MIN_CANDIDATES_PER_BLOCK` is 32 against KiCad's 8, for the same reason.
- `RuleResolver` keeps no `Send + Sync` bound. The parallel section never reaches the resolver (the clearance phase stays sequential, as KiCad's at `pns_node.cpp:346`), and a bound would stop a host from memoising behind a `RefCell` the way KiCad's own resolver does (`pns_kicad_iface.cpp:222`). If the boundary ever moves, the bound moves with it.

## Milestone 9, slice 6: component drag

Tags: #dragger #decision #deviation #kicad #testing #librepcb

- `src/component_dragger.rs` holds `COMPONENT_DRAGGER` in full. The whole class is 275 lines of C++ including the licence header, and it is the odd one out: no shove, no walkaround, no optimizer, no mode, no failure path. `Drag` returns true unconditionally (`pns_component_dragger.cpp:243`), tests no collisions and reads no routing mode, so a component drag behaves like mark obstacles whatever the session is set to, and the one collision query in the algorithm is the one `FixRoute` runs at commit time (`:253`). The dead `class OPTIMIZER;` forward declaration in the header (`:32`) is the trace of an intention that was never carried out.
- **`CommitDiff` gained `moved_solids: Vec<(HostId, Vec2)>` and `PreviewFrame` gained the same list.** KiCad does not delete and re-create a pad either: the router reports the removal and the addition like any other item and `PNS_KICAD_IFACE` intercepts both, `RemoveItem` recording the old position and returning without touching the commit (`pns_kicad_iface.cpp:2629`), `createBoardItem` recording the new one and returning `nullptr` (`:2849`), and `Commit()` then moving each pad's *footprint* by the difference, de-duplicated per footprint (`:2918`). The crate computes the same pair where it is known rather than reconstructing it from the diff, and de-duplicates by host object, which is one level further in than KiCad's footprint set: a pad that became one solid per padstack layer appears once. Both lists default empty, so every existing consumer and every stored fixture is untouched, and the event log writes a `moved-solid` record only when there is one.
- **`RouterState::DragComponent` exists and `pending_update` has a branch for it, which KiCad does not.** `ROUTER::GetUpdatedItems` handles `ROUTE_TRACK` (`pns_router.cpp:839`) and `DRAG_SEGMENT` (`:844`) and falls through for `DRAG_COMPONENT`, so a component drag reports an empty delta to everything that asks, the QA player included. That is note 06 erratum E15, and it is the **one** thing this slice adds rather than transcribes: an empty answer is not a behaviour a host could want and the branch it belongs in was already written.
- **`StartError::ComponentDragUnsupported` is gone rather than renamed.** Every shape of a non empty item set now has an algorithm: all solids is a component drag, more than one segment or arc is a multi drag, anything else is the single dragger. The LibrePCB fork names the variant in five files and needs it deleted at the next submodule bump; `SUGGESTIONS.md` has the list, together with `ffi_pnsrouter_is_dragging`, which tests `RouterState::DragSegment` and has to become "either drag state" now that there are four states.
- Three of note 06's eight component drag errata are repaired because the repair is invisible on a well formed board: **E31**, the two `std::set` of raw pointers, are uid ordered vectors here, which `DESIGN.md` section 8 requires; **E32**, `Start` clearing none of its three collections, which is latent only because KiCad allocates a fresh dragger per gesture; **E33**, the two "runs between two dragged pads" tests counting `SOLID_T` links and then walking every link, which is the filter the count already promised. E29, E30, E34 and E35 are reproduced with a comment each.
- **E36 is new and was found by writing the test.** The unconnected trace end block (`:137` to `:149`) asks for a joint on the *same net* as the pad and then asks whether its segment *collides* with the pad, and a same net pair takes `clearance = -1` at `pns_item.cpp:188` and never collides. So on an ordinary board a trace end that stops inside a pad without being jointed to it is not dragged along at all. Two ways through survive and both are real: a netless pad with a netless end inside it, because `:188` also requires `aHead->Net()` to be non null, and any board carrying a user defined physical clearance rule, because `runPhysicalOnly` makes the resolver net blind. The code is reproduced as it stands and `tests/component_dragger.rs` exercises the netless case; `SUGGESTIONS.md` proposes raising it upstream rather than deviating.

Without it two pads would share one drill and the hole to hole rule would report the pad colliding with itself.
- The clone keeps the original's uid, which is this crate's single `Item::clone` rule, and its provenance, so a moved pad still answers for the same host object and the commit can re-point the host map from the old solid to the clone.
- **The eleven corpus goldens are unchanged.** Ten match and `issue23449-shove-lone-via-drag-crash` misses by the same two added and one removed it missed before this slice; no corpus log holds a `DRAG_COMPONENT` session, so nothing here could have moved one. `tests/component_dragger.rs` is the coverage instead, six scenarios, and eight unit tests sit beside the code.

## Milestone 10, slice 2: the optimizer's pair path and `SimplifyLine`

- `src/optimizer.rs` gained `Optimizer::optimize_diff_pair`, KiCad's `OPTIMIZER::Optimize( DIFF_PAIR* )` (`pns_optimizer.cpp:1538`), with `merge_dp_segments`, `merge_dp_step`, `coupled_bypass`, `verify_dp_bypass` and `find_coupled_vertices`. That is note 07 section 6's answer to the brief's question about pair specific optimizer flags: there are none, in either direction, and `SetCollisionMask` is inert here for the same reason it is inert everywhere else.
- **What decides is coupled length.** `budget = clenPre / 10` is computed once per `merge_dp_step` call and both acceptance tests are `new - old + budget >= 0`, so a merge may cost at most a tenth of the coupling the pair had. KiCad's "fixme: come up with something more intelligent here" (`:1444`) is left where it stands.
- **Erratum E14's missing bound is `MERGE_PASS_LIMIT`**, the constant the single line `merge_full` and `merge_obtuse` already use. KiCad's `while( 1 )` leaves only through `step_p < 1 && step_n < 1` while the two counters fall only in a pass where neither lane merged, so a `mergeDpStep` that keeps succeeding without shortening a chain spins forever. The bound lives in a private `merge_dp_passes` that answers how many passes it took, so the deviation is a value a test reads rather than an argument about termination; `merge_dp_segments` calls it with the constant and returns KiCad's unconditional `true`, which is not a "something changed" flag and must not be read as one.
- **E14's other half is transcribed rather than repaired.** A span length of exactly one satisfies neither the `step > 1` merge guards nor the `step < 1` exit, so it costs one wasted pass per lane. Removing it would change how many passes a pair takes, which is now observable through the bound, and it changes no geometry. E15, `checkDpColliding`, has no caller anywhere and is not ported; `verifyDpBypass` does its two lines inline.
- **The lane to lane test inside `verifyDpBypass` is an ordinary clearance test**, not the forced pair gap `attemptWalk` installs before its shove. So the optimizer will bring the two lanes closer together than the gap the route was fitted at whenever the netclass clearance allows it, and only the coupled length score pushes back. Worth knowing before the placer slice reads a surprising result out of it.
- Two deviations at the line: KiCad's `int vStartIdx[1024]` with its own "fixme: possible overflow" comment is a `Vec`, and `coupledBypass` reads `aRefBypass.CPoint( 0 )` and `CSegment( 0 )` unguarded where a bypass between two coincident points is a single point chain with no segment, so that case answers `None` here instead of indexing out of bounds. `findCoupledVertices` answers segment indices that `coupledBypass` then reads as point indices; segment `i` starts at point `i`, so the conflation is harmless and is transcribed.
- Four unit tests carry the path, and all four matched the hand worked geometry on the first run: a pair with the same spike on both lanes merges to two straight runs and comes out *more* coupled than it went in, 2e6 to 4e6, because `coupledBypass` straightens the N lane in the same step and its score is coupled length alone; the same pair with a solid on each of the two straight runs comes out untouched, and both solids are needed, because with only the one on the P run the N lane still straightens on its own and `coupledBypass` wins with the candidate that leaves P exactly as it is; a pair whose only obtuse span holds its whole coupled run is refused, because the bypass would take the coupled length to zero against a budget of 2e5; and a twenty segment right angle staircase, which has no obtuse span at any length, takes nineteen passes unbounded and exactly three when held to three.
- **One thing note 07 section 6.3 leaves out, and it is a real behaviour.** `verifyDpBypass` builds its two lines with `LINE( const LINE&, const SHAPE_LINE_CHAIN& )` over `PLine()` and `NLine()`, and that constructor sets `m_via = nullptr` (`pns_line.h:90`) right after `updateLine` attached the pair's end via (`pns_diff_pair.h:491`, `:545`). So a pair that ends with vias is verified without them and a bypass whose end via would collide is accepted. The crate inherits it for free, because `Line::with_chain` already drops the via for the same reason; it is documented at the line rather than repaired, and the pair placer slice should know about it before it reads a surprising result.
- `topology::simplify_line` is in, and the "what is not here" list of `src/topology.rs` lost its entry. It reads only the first link of the line it is handed: the geometry it simplifies is whatever `World::assemble_line` finds from there, which can be longer than the caller's line. It uses `Simplify` and not `Simplify2`, and it rewrites the node by remove plus add, so every segment of the track is a new `ItemId` afterwards and a caller holding one has a stale handle. KiCad has the same property; it is only less visible there because the items are pointers into a pool.

## Milestone 10, slice 3: the pair placer, the `Placer` enum and the facade

Tags: #diffpair #placer #facade #decision #kicad #testing

- `src/placer/diff_pair_placer.rs` is steps 8 to 10 of note 07 section 14 in one go, because the three mode routines share `routeHead` and splitting them would have meant landing a placer with two thirds of its `route` unreachable. `DiffPairPlacer` with `find_dp_primitive_pair`, `dangling_anchor`, `start`, `init_placement`, `route_head`, `propagate_dp_head_forces`, `attempt_walk`, `try_walk_dp`, `rh_mark_obstacles`, `rh_walk_only`, `rh_shove_only`, `move_to`, `fix_route`, `commit_placement`, `abort_placement`, `toggle_via`, `set_layer`, `flip_posture`, `update_sizes`, `traces`, `current_node`, `current_nets` and `update_leading_rat_line`.
- **A fixed leg is not committed to the board any more; the session is.** KiCad's `FixRoute` ends with `CommitPlacement()` (`pns_diff_pair_placer.cpp:863`), so every leg of a pair reaches the board as it is clicked, and `initPlacement` then branches the router's root again. The crate's facade answers a host with one `CommitDiff` at the end of a session and `FixOutcome` has no room for a diff on its "carry on" arm, so a fixed leg stays in the node it was written into, the next leg branches **that** node rather than the root, and `commit_placement` folds the lot once. The geometry a session produces is the same; what differs is when the host sees it. Two consequences worth writing down: `init_placement` must not kill the children of the node it branches from when that node holds a fixed leg, and `Placer::commit_node` answers `None` until a leg is fixed, which is what keeps an abandoned shove mode session from committing whatever the shove pushed aside.
- **`DpPrimitivePair` cannot hold two `ItemId`s after all**, which note 07 section 12.1 assumed it could. `EndingPrimitives` (`pns_diff_pair.cpp:764`) is what tells the next leg where to start, and neither of the two things it answers with is a board object: without vias it builds two `SEGMENT`s on the stack out of the last segment of each lane, and with vias it hands over the pair's own two `VIA` members, which `FixRoute` clones into the node separately. So the primitive became `DpPrimitive`, an enum over an arena handle, a bare `Seg` and a bare via (position, layers, diameter), and every reader in `src/diff_pair.rs` goes through it. The alternative, storing the two throwaway segments in the arena, would have leaked two items per fixed leg or needed a detached item lifetime the world does not have; the alternative of looking the committed segments up again is wrong, because `SimplifyLine` runs between the add and `EndingPrimitives` and can merge exactly the segment that would be looked up.
- Errata, all transcribed with a comment at the line. E3: `attemptWalk`'s winding flag and `tryWalkDp`'s node argument are never read, so the four walk attempts are two computations run twice; two run here, which keeps the tie break (the first attempt wins under a strict `<`) and halves the walk cost of every move in walk and shove mode. E8: the coupled item search ties on `(distance, uid)` rather than on allocation address, which is `DESIGN.md` section 8. E9: `propagateDpHeadForces` keeps a running maximum force across every obstacle and every layer, displaces the virtual head by it on each round, and then answers `aP + force`, one application of the last maximum, which is not where the head ended up; `totalForce` is dropped because nothing reads it. E11: `tryWalkDp` always reports success, empty chains included, and minimises coupled length where every other comparison in the tree maximises. E12: `routeHead`'s failure return is sticky, and on that path the trace's gap is left as the centre to centre pitch, which `attemptWalk` then hands the shove as a copper gap. E2 and E13 are not ported at all: `setInitialDirection` is declared and never defined, and `m_orthoMode` is written three times and read never, so `Placer::set_ortho_mode` is a no op for a pair.
- **`Placer` is finally an enum with two variants**, as note 03 section 9.2 asked for when there was only one. `src/router.rs` holds `Option<Placer>` and dispatches; the single track call sites are unchanged except that three of them now pass the world and the context, because the pair placer's `ToggleVia`, `FlipPosture` and `SetLayer` re-run the move and the single placer's do not. `Placer::trace` is the `Traces()[0]` downcast KiCad performs in `Finish`, `ContinueFromEnd` and `GetNearestRatnestAnchor`, named rather than hidden: for a pair it is the P lane, and the N lane follows because the placer snaps the pair to the target once the cursor lands on it.
- **`start_routing_diff_pair` rather than a mode field**, which is what note 07 section 12.4 recommends and why: a pair start really does have different preconditions (a start object is required, `pns_router.cpp:345`), a mode field would make `start_routing` fallible in a way its signature does not show, and the recording then needs one more event rather than a mode event whose position in the stream would matter. Six new `StartError` variants carry the pair specific refusals, and `is_starting_point_routable_diff_pair` is the gate; the per item routability scan the two gates share moved into `check_hovered_items_routable`.

The crate has no net names, LibrePCB has no pair concept, and note 07 section 15.2 says not to invent a convention here. It wraps `FixedClearance`, answers the three hooks from two fields and forwards the rest, and it is public because a host with one pair can use it as it stands.
- `PreviewFrame` gained `via_n` and `ratline_n`. A pair draws two vias and two rat lines (`movePlacing` loops over the traces, `updateLeadingRatLine` draws one per lane), and both fields are `None` for every single track session, so no existing host code changes.
- The fixture is `tests/diff_pair_placer.rs`, note 07 section 15's board with **two** obstacles rather than one. The crossing track is what walkaround mode goes around and what mark obstacles mode reports; a second track running alongside the P lane is what shove mode pushes, because a track crossing the route at a right angle has nowhere to be pushed to and the shove correctly refuses. Coupling is asserted through `DiffPair::coupled_length` and `skew` over the committed geometry, as section 15.3 asks.

## Milestone 11, slice 1: the meander shape generator and the length arithmetic

Tags: #meander #geometry #deviation #kicad #testing

- `src/meander.rs` is steps 1 to 4 of note 08 section 13: the settings and status types, the shape generator, the fitting loop and the shared placer arithmetic. It needs no world, no rule resolver and no placer, which is the point: KiCad's `MEANDER_SHAPE` holds a `MEANDER_PLACER_BASE*` back pointer to reach three things, and all three go into a borrowed `MeanderContext` instead, so the generator is a pure function and the whole slice is unit testable.
- **Decision: the turtle rounds where KiCad truncates.** KiCad carries the turtle's position in a `VECTOR2D` and truncates each coordinate toward zero on append (`pns_meander.cpp:486`, `:513`, `:515`, `:518`, plus the implicit `VECTOR2D` to `VECTOR2I` conversions at `:625`, `:650`, `:652` and `:674`); this port carries it as a `Vec2` and rounds through `Vec2::resize` at every step, which is what `DESIGN.md` section 2 asks for. The two agree exactly on an axis aligned or 45 degree base segment, which is every trace KiCad's or LibrePCB's 45 degree router can produce, and differ by at most a nanometre per turtle step otherwise. The visible consequence is that erratum E15's asymmetry is gone: a meander to the left of the origin **is** the exact mirror image of the same meander to its right, where KiCad's is biased toward the origin by up to a nanometre per vertex. `the_same_meander_left_and_right_of_the_origin_is_a_mirror_image` pins it, so a future change to `resize` shows up as a test change.
- **E15 survives where the truncation is of a scalar rather than a coordinate.** Two sites assign a fractional expression to an `int` and both keep truncating toward zero: `cornerRadius`'s chamfer floor `m_width / 2 * ( 1 - tan( 22.5 deg ) )` (`:439`) and `MinAmplitude`'s correction `m_width * tan( 1 - tan( 22.5 deg ) )` (`:421`). Those are not turtle state, the rest of the milestone measures against them, and rounding them would move the corner radius window by a nanometre for no gain.
- The three transcendental constants are `f64` literals, not closed forms. `1 - tan( DEG2RAD( 22.5 ) )` and `2 - sqrt( 2 )` are one unit in the last place apart, and so are `tan( DEG2RAD( 22.5 ) )` and `sqrt( 2 ) - 1`, so note 08 section 8.2's suggestion to reach for `SQRT_2` would have been a silent deviation. `the_chamfer_constants_are_the_ones_kicad_computes` compares each literal bit for bit against KiCad's own expression, `DEG2RAD`'s `deg * M_PI / 180.0` association included; `f64::to_radians` multiplies by `PI / 180` instead and lands on the other value.
- **The round style needs a second enum, not just a missing variant.** `CornerStyle` is `#[non_exhaustive]` with `Chamfer` alone, as the note asks, but a value has to be expressible before it can be refused, so `MeanderStyle` is KiCad's `MEANDER_STYLE` in full with its discriminants and `MeanderSettings::new` is where the round half becomes an error. A host with a stored "rounded" flag now has somewhere to put it and gets told, rather than silently receiving chamfers that miss the target by about 0.62 radius per meander.
- **Erratum E22 is closed at the boundary rather than reproduced.** `MeanderSettings` has private fields and one fallible constructor, because a zero step turns `Fit`'s amplitude loop and both of `MeanderSegment`'s exits into an infinite loop. Everything else KiCad accepts is accepted: a negative amplitude, a radius percentage over 100 and an inverted length window all have defined behaviour and none of them can make a loop run away.
- Errata transcribed with a comment at the line: E3 (`MinAmplitude`'s `tan( 1 - tan( 22.5 deg ) )` typo, 13.3 percent too large, masked whenever the minimum amplitude setting dominates), E6 (the skip advance's corner radius term is always zero, so the simplified `spacing + step` is written), E7 (`CheckSelfIntersections` looks at chain 0 only, so a dual meander's N lane is never checked; the note wanted both tested, the brief wanted the erratum), E8 (the amplitude search's fast path measures the minimum amplitude and returns the initial guess), E16 (the bisection's collapsed interval answers without measuring), E17 (`Fit`'s dead first `m_baseSeg` assignment, only the live one written). E1's dead members and E4's `MT_ARC` are not carried at all.
- **`flipInitialSide` comes out as a flag.** It is the one place in KiCad's router where the shape generator writes back into its placer, and `meander_segment` answers `MeanderSegmentResult { initial_side_flipped }` instead. That is sound and not just tidier: nothing inside the fitting loop reads `m_initialSide`, so the write only changes where the *next* move starts. KiCad's lambda can fire more than once per loop and each firing negates, so the flag is the parity.
- **E11 is a speedup, not a behaviour.** KiCad resolves the clearance inside `spacing()`, which runs from `cornerRadius()`, from `genMeanderShape()` and twice per iteration of the fitting loop, and every one of those rebuilds the placer's whole trace before issuing an uncached rule query. Here `clearance()` is a free function the placer calls once per move and the answer sits in the context. Nothing in a move calls back into the host, so the rules cannot change underneath it.
- Twenty nine unit tests, and the geometry ones matched on the first run. The anchor case of note 08 section 2.6 is transcribed as literals from the note's hand computation, not read out of the port: corner radius 240000, the nine point chain ending at `(1200000, 0)`, a current length of 2637644 over a baseline of 1200000. The four closed forms are asserted on five amplitude and spacing combinations each, point list and length. `tune_line_length` lands within eleven nanometres of nine different target elongations on a 10 mm segment, against KiCad's own hundred thousand nanometre acceptance window.
- **Note 08 has one error found against the source.** Section 1.2 says `MEANDER_TYPE` has nine members and section 13 step 1 then asks for "seven variants; omit `MT_ARC`". Nine minus one is eight, and the port has eight. The other thing worth flagging is that section 3.1's description of `AddMeander` advancing to "the clipped base segment's far end" reads as if it disagrees with the code's `aShape->BaseSegment().B` (`pns_meander.cpp:930`), but `BaseSegment()` returns `m_clippedBaseSeg` and not `m_baseSeg` (`pns_meander.h:322`), so the note is right and the accessor's name is the trap.

## Milestone 11, slice 2: the tuning path, the length metric and the single trace placer

Tags: #meander #topology #placer #facade #decision #deviation #kicad #testing

- `topology::assemble_tuning_path`, `walk_tuning_path` and `find_lines_from_via` are in, and the "what is not here" list of `src/topology.rs` lost its length tuning entry. The walk differs from `follow_branch` in exactly the three ways a tuned length needs: it walks **through** a pad instead of stopping at one, it walks through a via by way of the spatial `findLinesFromVia` rather than through the via's joint, and its visited set is per path and grows as it goes, where `followBranch`'s is shared and never grows. KiCad's `WALK_RESULT` starts its length at minus one and not at zero, so a dead end that walked nowhere still replaces the initial value and clears the terminal pad; `a_walk_out_of_a_dead_end_finds_nothing_but_reports_zero` pins it. The wall clock timeout becomes a state budget, as `follow_branch`'s already had.
- **A plain chain sum replaces `ROUTER_IFACE::CalculateRoutedPathLength`.** `topology::path_length` sums `LineChain::length` over the path's lines and adds nothing for a via. Four terms of KiCad's number are gone and each is genuinely zero here rather than approximated: pad to die length, because nothing on `Item` carries one; via height, because a via is a point; the two in place chain fixups `AssembleTuningPath` ends with, `OptimiseTraceInPad` and `OptimiseTraceInVia`, because both are `LENGTH_DELAY_CALCULATION` members in KiCad's board code that need a `PAD` or a `PCB_VIA` and a board layer; and the whole propagation delay half, which needs a stackup model. Note 08 section 11.2 item 3 offers an optional `RuleResolver` hook for the via height; none is added, because nothing asks for it yet and a host that wants any of these folds its own term into the target it asks for. The consequence to know: a track that overshoots into a pad measures as it is drawn, where KiCad clips it to the pad's entry point first.
- `find_lines_from_via` takes the resolver, where `assemble_trivial_path` does not, because it is a `QueryColliding` and not a joint walk. Only the fallback half of KiCad's anchor test is ported, the one that asks the router's own via shape (`pns_topology.cpp:589`); the `IsPointInsideViaPad` half needs a `PCB_VIA`.
- **`Placer::commit_node` answers `None` until a tuning session has fixed something**, which is not what note 08 section 11.4 proposed. The note suggests answering `m_currentNode` as soon as a move has produced one. That is wrong here for a reason the note could not see from KiCad: `Start` removes the tuned track from the placer's own branch (`pns_meander_placer.cpp:102`) and `doMove` puts nothing back, so committing a move's scratch branch would delete the track and add nothing. The pair placer's `fixed_node` arrangement is reused verbatim, which also closes erratum E13 by construction.
- **The clearance is resolved once per session, not once per move.** Note 08 section 11.4 asks for once per move to remove erratum E11's per amplitude rule query and trace rebuild. Once per session is the same answer for a stronger reason than "the rules cannot change during a move": a `RuleResolver` belongs to the `Router` for the session's whole life and nothing anywhere in a tuning session calls back into the host. It sits in the tuning state and both `spacing_step` and every `MeanderContext` a move builds read it from there.
- Errata transcribed with a comment at the line: E10 (`CheckFit`'s `width + spacing` self intersection clearance, which is a heuristic and not a rule, and which gets *stricter* as the user widens the spacing), E18 (`doMove` adds the two corner shapes `MeanderSegment` already adds, so a base segment carries four where two would do; harmless, because a corner is a one point chain and `Append` drops a repeat). For this placer the two are the same value, since `Move` passes the one as the other, so the behaviour is identical and only the skew placer of the next slice will see the difference. E13 cannot arise, per the `commit_node` entry above. E11 is the clearance entry above.
- **An unconstrained target is KiCad's sentinel, not a short circuit.** Note 08 section 11.3 flags that `MeanderSettings::target_length` of `None` and a `Some` with a huge optimum behave differently in `doMove` and asks for one to be picked. KiCad's own value is picked: `None` resolves to `LengthTarget::unconstrained()`, minimum zero and optimum and maximum one kilometre, so an unconstrained session meanders as hard as the stretch allows and reports `Tuned`. `a_session_with_no_target_meanders_as_hard_as_it_can` pins it against the geometry a plainly unreachable target produces.
- **`start_tuning` takes the settings and no layer.** The layer is read off the clicked segment (`pns_meander_placer.cpp:435`) and `SetLayer` is not overridden by any meander placer, so a layer argument would be a lie; the sizes are dropped on the floor by KiCad too, for the same reason. `isStartingPointRoutable` has no arm for any of the three tuning modes, so there is no start gate at all and the placer's own `Start` is the only refusal. Three new `StartError` variants carry it: no object, not a track, and no tuning path. The third has no KiCad counterpart, where an empty `AssembleTuningPath` leaves the baseline at zero and every target then reads as too short; it cannot arise from a segment start in either tree, and it is a refusal here so that a host that reaches it learns why.

A `TuningInfo` carries a whole `MeanderSettings`, which is what a host reads the initial side flip back off, and a frame is returned by value from every `move_to`; unboxed it pushed `FixOutcome` past clippy's variant size threshold, which is a real signal and not a lint to silence. Its `target` field is the window the status was actually decided against, which is not the same thing as `settings.target_length()` when that is `None`.
- The three new events carry a `meander <block> <key> <value>` record type modelled on `settings` and `sizes`, with one difference stated in the grammar: there is **no block zero for the router's own value**, because a `Router` has no meander settings of its own, so the blocks are numbered from zero in the order the `start-tuning` events appear. A block is checked through `MeanderSettings::new` as it is read, so a file with a zero step or a round corner style is a parse error at the event's line rather than a settings value nothing downstream can honour. `FORMAT_VERSION` is unchanged at 1: the additions are new keywords, which an older reader rejects rather than misparses, and every stored fixture is byte for byte what it was.
- **The side flip has to be applied between base segments, not at the end of a move.** `doMove` re-reads `m_settings.m_initialSide` at the top of every base segment (`pns_meander_placer.cpp:265`) and `flipInitialSide` writes into it from inside `MeanderSegment` (`pns_meander.cpp:282`), so a flip on the first base segment of a tuned stretch decides which side the second one starts on. Slice 1's `MeanderSegmentResult` doc read as if the flip could be deferred to the end of the move; it can be within one base segment, which is all `meander_segment` sees, and cannot across them. `do_move` carries the side as a local it updates per segment and only the parity reaches the placer's settings, and the doc comment now says which of the two loops the claim is about. `MeanderSide::Default` negates to itself, so a stretch following the cursor never changes side, which is KiCad's `-0 == 0`.
- The fixture is `tests/meander_placer.rs`, note 08 section 14.2's board. Two things it does **not** cover, both said out loud in the file and in the work item. `an_obstacle_flips_the_initial_side` is unreachable on this board: the amplitude scan finds a shorter meander on the same side before it ever needs the other one, so `flipInitialSide` does not fire and the readout comes back on the side it started on. And there is no upstream anything to check the tuner against, so its fidelity rests on the hand computed shape assertions of slice 1 and on the errata being deliberate.
